# Vexa — ручне функціональне та безпекове тестування

Документ є артефактом тестування за розділом 21 ТЗ. Він описує ручні кейси для ролей
`GUEST`, `STUDENT`, `AUTHOR`, `ADMIN` і окремий набір негативних/безпекових перевірок.

> **Статус проходу на production:** `PENDING`. За планом команди фінальний прохід і
> заповнення колонки «Результат» виконується після наповнення production 28.09.2026.
> До цього моменту не можна позначати кейси як `PASS` без фактичної перевірки.

## Як фіксувати результат

- `PASS` — фактичний результат збігається з очікуваним.
- `FAIL` — знайдено відхилення; в «Примітці» додати посилання на issue.
- `BLOCKED` — перевірка неможлива через відсутні дані/зовнішню конфігурацію.
- `PENDING` — ще не виконувалось.

Для кожного прогону записати дату, середовище/URL, commit SHA або release tag і
тестовий обліковий запис (без паролів/токенів).

## 5. Безпека й негативні сценарії

| ID | Перевірка | Кроки | Очікуваний результат | Production |
|---|---|---|---|---|
| SEC-01 | Платний контент без покупки | STUDENT без enrollment викликає API закритого уроку | `403`, контент/URL відео не повертаються | PENDING |
| SEC-02 | Чужий draft/unpublished курс | Інший користувач відкриває пряме посилання/API | `404` або документований deny; метадані чернетки не витікають | PENDING |
| SEC-03 | Чужий ресурс автора | AUTHOR B змінює course/module/lesson AUTHOR A | `403/404`, ресурс не змінений | PENDING |
| SEC-04 | Чуже сповіщення | PATCH read із id іншого користувача | `404`, readAt не змінений | PENDING |
| SEC-05 | SQL injection у пошуку | Запити `%' OR 1=1 --`, `'; DROP TABLE users; --` | 200/400 без SQL error; результати лише за нормальними правилами | PENDING |
| SEC-06 | XSS у пошуку | Пошук `<script>alert(1)</script>` | Скрипт не виконується; текст екранується | PENDING |
| SEC-07 | XSS у відгуку | Створити відгук `<img src=x onerror=alert(1)>` | При відображенні JS не виконується | PENDING |
| SEC-08 | Невалідний JWT | Підставити змінений/прострочений access token | `401`, захищені дані не повертаються | PENDING |
| SEC-09 | Повторне використання OAuth exchange code | Використати той самий code двічі | Другий exchange відхилено | PENDING |
| SEC-10 | OAuth state/CSRF | Callback з невідомим/простроченим state | Авторизація не створюється | PENDING |
| SEC-11 | Rate limit | Перевищити частоту login/password change | `429` без зміни даних | PENDING |
| SEC-12 | 5xx без витоку деталей | Штучно викликати серверну помилку на staging | Клієнт отримує generic 500; подія є в Sentry без токенів/body | PENDING |
