Как мы ведём задачи, ветки и код-ревью в репозитории Vexa. Один цикл: issue → ветка → коммиты → pull request → ревью → squash в develop. Всё остальное в этом документе — детали этого цикла и что делать, когда он ломается.

Репозиторийgithub.com/terekh373/Vexa
Локальный путьC:\diploma\vexa
Ветка по умолчаниюdevelop
Стратегия мерджаsquash only
Команда4 разработчика

Одно направление движения. Ветка всегда отходит от develop и возвращается в него одним squash-коммитом — сколько бы коммитов вы ни сделали внутри. В main код попадает только релизом, вручную и только через тимлида. Обратного пути нет: develop не мерджится в feature — вместо этого ветку обновляют через rebase.

01

Где мы сейчас

Состояние на начало Sprint 3. Раздел обновляется каждый спринт — если он расходится с реальностью, скажите тимлиду.

ЧтоСостояние
Монорепоapps/api, apps/web, apps/mobile, packages/shared
База данныхСхема целиком: 24 модели, 21 enum, две миграции, seed с демо-контентом
Auth APIregister / login / refresh / logout / verify-email / me, argon2, rate limiting
Курсы APIGET /api/courses/:id, /:id/reviews. Каталог — в работе, issue #3

Веб-клиент пишется на JavaScript, не на TypeScript. Это решение тимлида, зафиксированное в «Змінах №1 до ТЗ». Бэкенд, packages/shared и мобилка остаются на TypeScript со строгой типизацией. Никто не начинает миграцию фронта по своей инициативе.

Следствие важнее самого решения: раз на вебе нет типов, компилятор больше не ловит расхождения между клиентом и API. Эту работу теперь делает документ — см. раздел 06.

02

Модель веток

Три типа веток, у каждой своя роль и свой уровень защиты.

ВеткаРольКто пушитЗащита
main Стабильный код. То, что показываем на защите и деплоим в production. Только тимлид, только релизным PR из develop. PR + 1 апрув + Code Owners + все CI-чеки + up to date
develop Интеграционная ветка. Здесь собирается вся работа спринта. Ветка по умолчанию. Никто напрямую. Только через PR. PR + 1 апрув + Code Owners + все CI-чеки
feature/* Одна задача = одна ветка. Живёт не дольше спринта. Автор ветки, свободно, хоть сто раз в день. Нет

Прямой push в develop отклоняется — это не поломка. Так настроен ruleset protect-develop. Если git говорит protected branch hook declined — вы забыли создать ветку. Как это починить, не потеряв работу, — в разделе 08.

Bypass-списка нет ни у кого, включая тимлида. В августе один коммит всё-таки уехал в develop напрямую, минуя PR и ревью. Дыру закрыли. Если у вас получилось запушить в develop без PR — это баг настроек, сообщите, а не пользуйтесь.

Кто что ревьюит

Ревьюер назначается автоматически по файлу .github/CODEOWNERS — в зависимости от того, какие папки затронул PR.

ПутьВладельцы
/apps/api/Тимлид + бэкенд-разработчик
/apps/api/prisma/, /docs/schema.dbmlТимлид + бэкенд-разработчик
/packages/shared/Тимлид + бэкенд-разработчик
/apps/web/, /apps/mobile/Оба фронтенд-разработчика
всё остальноеТимлид (глобальный фолбэк)

packages/shared — это контракт между бэком и фронтом: карта маршрутов, типы ответов API и zod-схемы. Менять его в обход тимлида нельзя, иначе на интеграции фронт и бэк разъедутся.

03

Issues: зачем и как

Issue — карточка задачи внутри репозитория. Заголовок, описание, исполнитель, метки, статус open / closed.

Смысл не в бюрократии, а в сквозной связке. Каждый артефакт ссылается на предыдущий, и через месяц можно открыть любой из них и восстановить контекст:

связка
Issue #3  «api: каталог курсів — пошук, фільтри»
   ↓  ветка   feature/3-catalog-api-port
   ↓  PR      feat(api): catalog endpoints  → в описании «Closes #3»
   ↓  merge   squash в develop
   ↓  Issue #3 закрывается автоматически

Анатомия issue

ПолеЧто это
НомерСквозной счётчик, общий с pull request'ами. Поэтому в нумерации есть дыры — это нормально.
AssigneeОдин человек. Задача без исполнителя не делается никем.
Labelsmvp, second-queue, backend, frontend, infra, bug
MilestoneСпринт. Видно прогресс: «4 из 12 закрыто».
КомментарииОбсуждение решений. «Комиссию считаем до или после эквайринга?» — ответ остаётся в задаче, а не тонет в Telegram.

Формат описания

Три блока, ничего лишнего. Пишем по-украински — как и весь контент проекта.

шаблон issue
## Що зробити
Реалізувати GET /api/courses згідно з розділом 15.3 ТЗ і таблицею 3.

## Обсяг
- [ ] Пагінація, zod-схема query-параметрів
- [ ] Фільтри: тип контенту, категорія, клас, ціна, рейтинг, мова
- [ ] Сортування: relevance, popularity, rating, date, price_asc, price_desc
- [ ] У видачу потрапляють лише курси зі статусом PUBLISHED

## Готово, коли
Фільтри комбінуються між собою, чернетки недоступні
неавторизованому користувачу, контракт описано в docs/frontend-api-map.md.

Лейбл second-queue — главный инструмент против расползания объёма. Раздел 24 ТЗ называет scope creep риском с высокой вероятностью. Когда посреди спринта приходит идея «а давайте ШІ-підбір курсів» — не спорим, а заводим issue с этим лейблом. Идея не потеряна, спринт не сломан.

second-queue не значит «никогда». Значит «не берём, пока не закрыт весь mvp». Обратное тоже верно: если задача есть в разделе 3.3 ТЗ, повесить на неё second-queue нельзя — так, модерация курсов остаётся в MVP, потому что без неё не выполняется критерий приёмки из раздела 21.

Магические слова

В описании pull request (не в заголовке):

  • Closes #3 / Fixes #3 / Resolves #3 — issue закроется сама при мердже в develop.
  • Related to #3 — просто ссылка, без автозакрытия.
  • #3 в любом комментарии — превращается в ссылку. @ник — шлёт уведомление.

Сколько issues заводить

6–12 на спринт, крупными кусками. Микрозадачи вроде «поправить отступ в футере» — в чат, не в трекер. Иначе доска превращается в свалку, и по ней перестают ориентироваться.

04

Рабочий цикл в CMD

Восемь шагов от «взял задачу» до «issue закрыта». Повторяется для каждой задачи без исключений.

  1. Взять задачу

    Открываете Issues, находите свою (или берёте свободную из текущего milestone), ставите себя в Assignee. Если задача не ваша — сначала спросите в чате.

  2. Обновить develop и отойти от него

    Всегда от свежего develop. Ветка, отведённая от вчерашнего состояния, соберёт конфликты на ровном месте.

    cmd
    cd C:\diploma\vexa
git checkout develop
git pull
git checkout -b feature/3-catalog-api-port

  3. Работать и коммитить часто

    Коммит — это точка сохранения, а не отчёт о завершённой фиче. Делайте их каждые 30–60 минут осмысленной работы. Внутри feature-ветки история всё равно схлопнется в один squash-коммит, так что бояться «некрасивых» промежуточных коммитов не нужно.

    cmd
    git status                     :: что изменилось
git add .                      :: или git add путь\к\файлу
git commit -m "feat(api): add course filters"

    Первым делом после git status — глазами проверьте список файлов. Если там мелькнул .env, node_modules или *.tsbuildinfo — стоп, чините .gitignore, не коммитьте.

  4. Пушить в свою ветку каждый день

    Первый push требует -u, дальше достаточно git push. Код, который лежит только на вашем ноутбуке, для команды не существует.

    cmd
    git push -u origin feature/3-catalog-api-port   :: первый раз
git push                                        :: все следующие

  5. Перед PR — подтянуть develop

    За два-три дня develop уехал вперёд. Подтягиваем его изменения к себе через rebase, чтобы история осталась линейной, а PR показывал только ваши изменения.

    cmd
    git checkout develop
git pull
git checkout feature/3-catalog-api-port
git rebase develop

    Если появились конфликты — раздел 08. Если ветку уже пушили, после rebase нужен git push --force-with-lease (обычный push будет отклонён — это ожидаемо).

  6. Проверить локально то же, что проверит CI

    Четыре команды — по числу чеков. Красный CI на чужом PR отнимает время у всех, свой всегда дешевле починить до пуша.

    cmd
    npm run lint
npm run lint --workspace @vexa/web    :: oxlint, только фронт
npm run typecheck                     :: api, shared, mobile
npm run build

    typecheck намеренно не покрывает apps/web: там нет TypeScript, и включение web в проект компилятора давало бы зелёный чек, ничего не проверяя. За фронт отвечает lint-web.

  7. Открыть pull request

    На GitHub появится плашка «Compare & pull request», либо Pull requests → New. Проверьте направление: base = develop, compare = ваша ветка. В main — никогда.

    Заполняете шаблон, ставите Closes #3, назначаете ревьюера по CODEOWNERS. Дальше ждёте четыре зелёных чека и апрув.

  8. Squash and merge, ветку удалить

    Кнопка мерджа доступна только когда CI зелёный и апрув есть. Способ мерджа один — Squash and merge, остальные отключены в настройках репозитория. Заголовок squash-коммита = заголовок PR, поэтому он должен быть осмысленным.

    Ветка на GitHub удалится автоматически. Локальную подчистите сами:

    cmd
    git checkout develop
git pull
git branch -d feature/3-catalog-api-port
git remote prune origin        :: убрать ссылки на удалённые ветки

Ветка живёт не дольше спринта. Двухнедельная ветка с сорока файлами — это не PR, а мучение для ревьюера. Если задача разрослась, режьте её на две issue и два PR. Ориентир: не больше ~400 строк диффа.

Файлы через веб-интерфейс GitHub («Add files via upload») не заливаем. Так уже был потерян один PR: 84 файла легли в корень репозитория и снесли структуру монорепо. Код попадает в репозиторий только через ветку и git push.

05

Имена веток и коммитов

Две конвенции, которые нужно запомнить один раз.

Ветки

формат
feature/<номер issue>-<краткое-описание-латиницей>
fix/<номер issue>-<описание>
chore/<описание>          :: инфраструктура, конфиги, без issue
  • Только латиница, только нижний регистр, слова через дефис.
  • Хорошо: feature/12-course-player, fix/18-cart-total
  • Плохо: alina-dev, Vexa-front2, new-branch, feature/каталог, Fix_Bug2

Персональные ветки вроде alina-dev или Vexa-front2 запрещены отдельно: они живут месяцами, копят конфликты и в итоге не мерджатся вообще. Ровно это и произошло с Vexa-front2.

Коммиты — Conventional Commits

формат
<type>(<scope>): <описание в императиве, по-английски>

feat(api): add course catalog filters
fix(web): correct cart total calculation
chore(ci): cache npm dependencies
docs(readme): add local setup steps
refactor(api): extract payment service
test(api): cover commission calculation
typeкогда
featновая функциональность
fixисправление бага
choreконфиги, зависимости, инфраструктура
docsдокументация
refactorпереписали без изменения поведения
testтесты

Scope — это зона: api, web, mobile, db, shared, ci. Сообщения коммитов — по-английски, как и комментарии в коде. Описания issues, тексты интерфейса и контент БД — по-украински.

Не пишите update, fix, wip, ещё правки. Через месяц по такой истории невозможно найти, где сломалось. Заголовок должен отвечать на вопрос «что изменится в продукте, если применить этот коммит».

06

Контракт с бэкендом

Раз на вебе нет типов, расхождения клиента и API ловит не компилятор, а документ. Это самый хрупкий шов в проекте.

ФайлЧто в нём
docs/frontend-api-map.mdЭндпоинты, параметры, форма ответа, коды ошибок. Главный документ фронтенда.
packages/shared/src/routes.tsКарта URL фронтенда. Ссылки строим через неё, а не конкатенацией строк.
docs/schema.dbmlСхема БД. Имена полей берём отсюда, не выдумываем.

Изменил ответ API — обнови docs/frontend-api-map.md в том же PR. Это пункт чеклиста, а не пожелание. Документ уже один раз разошёлся с кодом: в нём была указана цена как priceAmount, тогда как API отдаёт price.amount. Такое расхождение стоит фронтендеру полдня и выглядит как «бэкенд сломался».

Что важно помнить всем

  • Деньги — целые копейки. 500 грн = 50000. Делить на 100 только при выводе на экран. Никаких float ни на клиенте, ни на сервере.
  • Права проверяются на сервере. Скрытая кнопка — это удобство, а не защита. Доступ к платному контенту сервер перепроверяет на каждом запросе.
  • Токены живут в теле ответа, не в куках. Access — 15 минут, refresh — 30 дней и одноразовый: после обновления старый мёртв.
  • На 403 refresh не делаем — это нехватка прав, новый токен не поможет.
  • Статусы курса: DRAFT → MODERATION → PUBLISHED / REJECTED → UNPUBLISHED. Гость видит только PUBLISHED.
07

Pull request и ревью

PR — это не формальность перед мерджем, а место, где ловятся ошибки до того, как они попадут в develop.

Что должно быть в PR

  • Заголовок в формате Conventional Commits — он станет текстом squash-коммита.
  • Closes #N в описании.
  • Как проверить — 2–3 шага, чтобы ревьюер не гадал.
  • Скриншот, если менялся интерфейс.
  • Чеклист из шаблона: входные данные валидируются zod, права ролей проверяются на сервере, деньги в целых копейках, секреты не попали в коммит, миграция добавлена, frontend-api-map.md обновлён.

Автору: до того, как звать ревьюера

  • CI зелёный — все четыре чека.
  • Дифф прочитан своими глазами во вкладке Files changed. Половина замечаний находится там же самостоятельно.
  • Нет закомментированного кода, console.log и отладочных заглушек.
  • PR делает одну вещь. «Заодно поправил ещё три файла» — отдельный PR.

Ревьюеру: за что смотрим

ПриоритетЧто проверяем
БлокируетПрава ролей проверяются на сервере, а не на клиенте. Доступ к платному контенту не открывается без покупки. Секреты не в коде. Деньги в целых копейках, не float. Есть миграция, если менялась схема. Ответ API изменился — обновлён api-map.
Просим поправитьНет валидации входных данных, есть any в TypeScript-коде, бизнес-логика уехала в контроллер, ошибки не обрабатываются или обрабатываются мимо AppError.
КомментарийИменование, дубли, читаемость. Не повод блокировать PR.

Ревью — в течение рабочего дня. Если PR висит больше суток, пишите автору напрямую: заблокированный человек стоит дороже, чем неидеальный код.

Свой PR апрувить нельзя. Это ограничение GitHub, не настройка. Поэтому у каждой папки в CODEOWNERS минимум два владельца — иначе PR владельца повиснет навсегда. Единственное исключение — /.github/: инфраструктурные PR тимлид проводит, разово отключая ruleset.

08

Когда что-то пошло не так

Пять ситуаций, которые случатся у каждого. Ни одна из них не требует удалять папку и клонировать заново.

Начал работать, забыл создать ветку

Коммиты ушли в локальный develop, push отклонён. Работа цела — её нужно перенести.

cmd
git checkout -b feature/3-catalog-api   :: ветка от текущего состояния, коммиты уехали с ней
git push -u origin feature/3-catalog-api

git checkout develop                     :: вернуть develop к состоянию сервера
git reset --hard origin/develop

git reset --hard безвозвратно стирает незакоммиченные изменения. Выполняйте его только после того, как убедились, что ветка с вашей работой запушена.

Конфликт при rebase

Git останавливается и показывает файлы с конфликтами. В VS Code они подсвечены, есть кнопки Accept Current / Accept Incoming / Accept Both.

cmd
git status                     :: список конфликтующих файлов
:: правите файлы в VS Code, убираете маркеры <<<<<<< ======= >>>>>>>
git add .
git rebase --continue

git rebase --abort             :: если всё запуталось — откат к состоянию до rebase

После успешного rebase ветка «переписана», поэтому обычный push будет отклонён:

cmd
git push --force-with-lease

--force-with-lease вместо --force: он откажется пушить, если кто-то успел добавить коммиты в вашу ветку. В feature-ветке это безопасно. В develop и main force-push запрещён ruleset'ом.

Ошибся в последнем коммите

cmd
git commit --amend -m "feat(api): correct message"   :: поправить сообщение

git add забытый-файл.ts                              :: дописать файл в последний коммит
git commit --amend --no-edit

git reset --soft HEAD~1                              :: отменить коммит, изменения оставить

Всё это безопасно, пока коммит не запушен. Если запушен — потребуется --force-with-lease, и делать так можно только в своей feature-ветке.

Случайно закоммитил .env

Репозиторий публичный, поэтому реагировать надо сразу.

cmd
git rm --cached .env           :: убрать из индекса, файл на диске остаётся
:: убедиться, что .env есть в .gitignore
git commit -m "chore: remove env file from tracking"

Этого недостаточно, если коммит уже улетел на GitHub. Ключ остался в истории и считается скомпрометированным. Порядок такой: перевыпустить ключ в сервисе (LiqPay, Cloudflare R2, Cloudflare Stream, Brevo), сообщить тимлиду, и только потом чистить историю. Удалить файл новым коммитом — не то же самое, что удалить его из истории.

Ветка отстала от develop на неделю

Если конфликтов много и rebase превращается в бесконечную правку — проще начать заново от свежего develop и перенести изменения руками. Это не поражение, это часто быстрее.

cmd
git log --oneline develop..HEAD     :: что есть у меня и нет в develop
git diff develop --stat             :: какие файлы затронуты

Отдельный приём, когда нужный код лежит в чужой или старой ветке, а её структура уже неактуальна — вытащить файлы точечно, не мерджа ветку целиком:

cmd

:: если путь в старой ветке другой — забрать содержимое файла в новое место

Правила команды

Договорённости, которые держат процесс. Не рекомендации.

Делаем

  • Каждая задача — своя ветка от свежего develop.
  • Пушим свою ветку минимум раз в день.
  • Прогоняем все четыре чека до открытия PR.
  • Пишем Closes #N в описании PR.
  • Ревьюим в течение рабочего дня.
  • Обсуждение технических решений — в issue, не в личке.
  • Новая сущность в БД — сразу миграция.
  • Изменил ответ API — обновил docs/frontend-api-map.md.
  • Не понял чужое решение в ревью — спрашиваем, а не апрувим молча.

Не делаем

  • Не пушим напрямую в develop и main.
  • Не заливаем файлы через веб-интерфейс GitHub.
  • Не апрувим PR не глядя, чтобы «разблокировать».
  • Не мерджим красный CI, отключая правило.
  • Не коммитим .env, node_modules, dist.
  • Не заводим личные ветки вида имя-dev.
  • Не держим ветку дольше спринта.
  • Не правим packages/shared и apps/api/prisma без тимлида.
  • Не берём задачи из second-queue, пока не закрыт mvp.
  • Не начинаем миграцию фронта на TypeScript по своей инициативе.
